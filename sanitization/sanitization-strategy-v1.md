## 一、脱敏目标

将三份签字放行的规格文档转换为可开源发布的 Solidity 合约代码，同时确保：

1. **合约接口可用**——开源社区/开发者可以理解框架结构、运行演示用例
2. **核心参数不泄露**——置信度阈值、分流比例、检测规则、延迟阈值等生产参数被脱敏
3. **部署不依赖开源代码**——生产环境通过链下配置+链上治理注入真实参数
4. **法律/合规安全**——Apache 2.0 开源，README 含免责声明

## 二、公开保留清单（开源可见，照实发布）

| 类别 | 内容 | 说明 |
|------|------|------|
| 合约接口 | `recordAudit()` / `emergencyPause()` / `emergencyUnpause()` / `verifySignature()` / `proposeNewAdmin()` / `approveNewAdmin()` | 全部函数签名保留 |
| 事件定义 | `event AuditRecorded(...)` / `event AdminChanged(...)` / `event CertificateDegradation(...)` / `event CertificateRestoration(...)` | 事件结构保留，但 `CERT_DEGRADATION` 的枚举值替换为 `string reason` 自由文字类型 |
| 存储结构 | `struct AuditEntry` / `mapping(bytes32 => AuditEntry)` | 骨架结构保留 |
| 角色定义 | `enum AuditConclusion`(APPROVED/REJECTED/REVISION_NEEDED) / `enum SignaturePhase`(PLATFORM/PKI) / `enum SigAlgorithm`(SHA256/SHA256WITHRSA/SHA256WITHECDSA) / `enum AuditType`(PRODUCTION/OVERSIGHT/CERT_DEGRADATION) | 枚举值全部保留（通用定义不改） |
| 签名阶段 | Phase 1（平台留痕）+ Phase 2（PKI证书签名） | 双阶段签名机制保留 |
| Merkle机制 | merkleRoot延迟填写 + Merkle批处理接口 | **保留接口概念和签名**，批次大小改为部署配置项 |
| 多签逻辑 | 3管理员 + 2/3阈值 + 替换流程 | **保留**——多签逻辑公开无害，且开源合约不含阈值反而奇怪 |

> **依据：** cn001补充了Merkle批次大小需要模糊化，hk001补充了CERT_DEGRADATION原因枚举改为自由文字。已综合纳入。

| 内容 | 理由 |

## 四、生产参数注入方案（方案C增强版）

### 4.1 架构

```
开源仓库
  ├── contracts/         ← 含演示值的 Solidity 合约（可编译可部署）
  ├── .env.template      ← 部署模板，注释写明参数含义和推荐范围
  └── README.md          ← 使用说明 + 免责声明

部署方
  ├── 复制 .env.template → .env
  ├── 填入自己的参数值
  ├── 合约部署时使用 .env 作为初始化参数
  └── 通过治理投票（多签钱包）覆盖演示值
```

### 4.2 合约默认值

**采用极保守值：**

| 参数 | 默认值 | 理由 |
|------|:-----:|------|
| 自动通过阈值 | 置信度≥99%自动通过 | 极保守，忘记配置也不会漏掉 |
| 抽审阈值 | 99%-80%抽审 | 同上 |
| 人工审核阈值 | <80%强制人工 | 同上 |
| 异常等级 | Level-1及以上全部强制人工 | 同上 |
| 紧急暂停状态 | `emergencyPaused = true` | 部署后由管理员手动解除，确保有人确认过 |

> **设计说明：** 极保守默认值的哲学是——最坏情况下让审核人工作量加倍，而不是让有害诊断溜掉。

### 4.3 参数升级的方向性检查

合约中增加方向性检查修饰符：

```solidity
// 参数升级只能向安全方向调整
modifier onlyTighter() {
    // 新阈值 不能高于 旧阈值（分流比例只能收紧）
    // 新延迟 不能长于 旧延迟（延迟只能缩短）
    _;
}
```

防止攻击者攻破多签后恶意降低安全参数。

### 4.4 治理覆盖投票门槛

参数覆盖投票至少需要 2/3 管理员签名（与管理员替换规则相同），不允许单人直接提交。此规则硬编码在合约中，不可通过治理投票修改。

## 五、开源合规

### 5.1 开源协议

**Apache 2.0**

- ✅ 专利授权条款保护贡献者和使用者
- ✅ 商业友好（医院系统商用无障碍）
- ✅ 不限制我们申请专利
- ❌ MIT：无专利条款，不适用
- ❌ GPL：强制衍生品开源，医院不愿意

### 5.2 README 必含声明

```markdown
⚠️ 免责声明
本仓库为框架参考实现，不包含生产级安全审计。
合约中的参数值为演示用途，不代表生产配置。
核心业务逻辑参数不在开源范围内，请通过部署配置或治理机制注入。
部署前请独立进行安全审计。
```

### 5.3 开源不包含的内容

| 不包含 | 理由 |
|--------|------|
| 任何真实医院数据样本 | 法律+合规风险（哪怕脱敏后） |
| 生产测试用例 | 防反推参数 |
| 审计链/信证链的完整规格文档 | 规格文档不公开，仅公开生成的代码 |
| 部署脚本中的真实参数 | .env 不在版本控制内 |

## 六、PR审核流程

### 6.1 三级审查制

| PR类型 | 审查级别 | 要求 |
|--------|:-------:|------|
| 文档/注释修正 | L1（轻） | 1人审 + CI通过 |
| 功能新增/重构 | L2（中） | 2人审 + CI通过 + 48小时review窗口 |
| 安全敏感变更（签名验证、存储结构、权限控制） | L3（严） | 3人审 + CI通过 + 7天窗口 + 至少1人非同一团队 |

### 6.2 CI最低配置

- Solidity linter 检查
- Foundry/Hardhat 测试套件（覆盖率≥90%）
- Slither 安全分析（无高/严重漏洞）
- 合约大小检查（不超过 EIP-170 的 24KB 限制）
- 二进制一致性检查（PR中的代码与发布的合约字节码匹配）

### 6.3 合入前红队检查

PR中任何修改过的代码，必须被另一个独立红队（非审查人，非提PR者）review一次。不要求逐行审，但必须确认没有明显恶意代码注入。

## 七、脱敏验证（hk001负责）

脱敏完成后、开源发布前，由 hk001 执行脱敏验证：

1. 语义搜索：在开源代码中搜索是否残留真实参数值（95%/8%/2%、3秒/5秒等）
2. 模式匹配：搜索是否残留 "美以"、"副主任医师" 等敏感引用
3. 接口一致性：确认公开合约的接口签名与规格文档定义一致
4. 输出：脱敏验证报告（PASS / 需修正）

验证不通过不发版。
